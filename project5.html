Scaling healthcare design with a shared system

A reusable foundation and component system created to reduce repeated design effort and improve consistency across products.

Challenge:

Every time we started a new project or started a new phase of the project we were creating projects from scratch. This would mean setting up a new components library each time.
This meant we were designing the same components over and over again with the style changing each time to suit functionality. We needed to:

  • Recreate old components
  • Gather all old use cases and create use cases for each component

Values for Company:

  • Consistency teams can trust: one source of truth for colour, type, spacing and components across web and app.
  • Speed without rework: designers stop rebuilding the same components and spend time on product problems instead.
  • Predictable experiences for users: familiar patterns mean fewer surprises and less relearning between products.
  • Room to scale: new features and products can be assembled from tested parts without visual drift.

Outcome / Benefits

  • Let them focus on solving complex problems, not pixel-perfect tweaks. Consistency is built-in.
  • Design resources can focus less on tweaking visual appearance and more on complex problems/solutions. This ensures that the project and designs are consistent visually and functionally.
  • Reduced development time and costs.

Beyond Pixels & Styles: Craft Experiences with Design Systems

Our journey began by establishing a well-defined hierarchy for our design system library. This strong foundation, built on essential components like color, typography, grid, spacing, and shadows, empowers us to create highly scalable products. With this robust base, we gain the flexibility to leverage any foundation library in the future when building new design system components for various applications, including provider apps and SaaS products.

Foundation Time with Figma Tokens:

After collaborative discussions and brainstorming, we've refined our design system vision and are now building a robust foundation using Figma's variables and tokens. This ensures consistency and efficiency when creating future components, accessible through our centralized foundation library.

Crafting Reusable Design Components:

We compiled a comprehensive list of existing components and anticipated future needs to build a versatile toolkit..

The component library consists of:


Component name:

A specific and unique UI component name, to avoid miscommunication between designers and developers. This needed to be clear so that the components would work as they were supposed to without error.

State changes:

Recommended defaults and the subsequent changes in appearance.

Note making:

Page annotations and descriptions to understand what component you were looking at.

Breakpoints:

Any size indication and breakpoints for the developers.

  • A clear explanation for what this element is and how it is typically used, occasionally accompanied by dos and don’ts for context and clarification.
  • Picture examples so that it was clear what we were talking about
  • Rules of when to use the component and how to use the component

What I would do next

Treat the system as a product: publish a changelog, run a contribution model with engineering, and track adoption — component coverage, detached instances and time to build a new screen — so the system earns its place in every team's workflow.

Outcome and evidence

Foundations and a documented component library delivered; adoption and efficiency metrics were not formally tracked.

What I would measure next

Component coverage across product files, detached-instance rate, time to build a new screen and handoff questions from engineering.
